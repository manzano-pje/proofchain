Estratégia recomendada (pragmática e de baixo risco) Objetivo: remover os acoplamentos indevidos e aplicar inversão de dependência sem grandes reestruturações.
Passo A (rápido e de baixo risco) — Remover dependências do shared para infra:
Mover classes de shared que dependem de repositórios específicos para o módulo adequado, exemplo:
Mover TenantValidation de com.proofchain.shared.util → com.proofchain.admin.institution.application (ou admin.institution.domain).
Justificativa: validação de tenant é regra ligada ao contexto institution — faz sentido viver no módulo admin/platform.
Mudança mínima nos imports: componentes que usavam TenantValidation continuam a chamá-la, mas importam do novo pacote.
Mover SystemBootstrap (se faz bootstrap de módulos específicos) para um pacote central do módulo admin ou projeto principal (ex.: com.proofchain.bootstrap) — evitar shared depender de infra.
Para UserDetailsServiceImpl: avaliar mover para user.interfaces/user.application (onde UserRepository já existe) ou converter para depender de uma abstração user.domain.repository.UserRepository (veja Passo B).
Por que este passo é seguro: apenas relocação de classes que pertencem semanticamente a um domínio; altera imports, pouco risco de break. Boa primeira etapa para reduzir acoplamentos imediatos.
Passo B (correto e sistemático) — Introduzir ports/abstrações de repositório no domínio:
Criar interfaces de port (contratos) em domain de cada módulo que exporta funcionalidade requerida por outros módulos. Exemplo:
Criar com.proofchain.admin.institution.domain.repository.InstitutionRepository (interface do domínio) com métodos usados (p.ex. boolean existsByIdAndDeletedAtIsNull(Long id)).
Modificar o repositório da infraestrutura para estender tanto JpaRepository quanto a interface do domínio, por exemplo:
infra: public interface InstitutionRepository extends JpaRepository<Institution, Long>, com.proofchain.admin.institution.domain.repository.InstitutionRepository { }
Depois, atualizar todos os imports nas classes que hoje importam com.proofchain.admin.institution.infrastructure.repository.InstitutionRepository para importar com.proofchain.admin.institution.domain.repository.InstitutionRepository.
Repetir para outros repositórios que são usados por múltiplos módulos (UserRepository, PlansRepository, etc).
Por que: com isso outros módulos passam a depender de uma interface estável (domínio) e não da implementação. Infra provê implementação concreta (Spring Data).
Passo C (refinamento) — Revisar shared e extrair apenas utilitários independentes:
Se algum utilitário do shared precisa de comportamento de módulos, ele deve depender de uma interface (port) definida em shared ou no domínio apropriado. Ex.: TenantValidation poderia depender de um TenantPort definido no shared e implementado em admin.institution.infrastructure — essa é alternativa se quiser manter TenantValidation no shared.

Riscos e mitigação
Risco: imports quebrados / compile errors — mitigar com refactor da IDE e testes de compilação contínuos.
Risco: regressão funcional (mudança de bean names) — mitigar com testes automatizados e validação manual de fluxos críticos (auth, criação de usuário, startup).
Risco: cortes em commits grandes — realizar muitos commits pequenos e testáveis.
Alternativas (trade-offs)
Alternativa rápida: apenas mover TenantValidation e UserDetailsServiceImpl para módulos donos (minimiza mudanças). Isso reduz o acoplamento imediato, mas mantém dependência de handlers para infra.
Alternativa completa (mais trabalho, melhor correção): aplicar ports para todos os repositórios compartilhados e padronizar nomes de pacotes.
